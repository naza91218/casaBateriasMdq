Capítulo 1

Resumen del proyecto

La Casa de las Baterías es un comercio de Mar del Plata con 45 años de trayectoria. Su diferencial es la colocación a domicilio incluida en el precio, la medición del alternador y 12 meses de garantía. El proyecto construye su tienda online propia con un principio rector: el cliente nunca tiene que saber de baterías; el auto lleva a la batería.

Objetivos

  • Que el comprador elija marca, modelo y año de su auto y vea solo las baterías compatibles, separadas en económicas y reforzadas.
  • Que compre como invitado, en una sola página, con Mercado Pago, transferencia con descuento o efectivo al retirar, y elija colocación a domicilio o retiro en el local.
  • Que el administrador (Mateo) gestione pedidos, catálogo, precios, stock, fotos y configuración desde un panel usable en el celular.
  • Avisos por mail en cada cambio de estado, presencia en Google (SEO local y buscadores con IA) y cumplimiento legal (Defensa del Consumidor y Ley 25.326).

Alcance cerrado. Por decisión de la constitución del proyecto quedan fuera: cuentas de cliente, turnos, cupones y precio para el canje de la batería usada (el canje es solo una consulta que se responde por WhatsApp).

Metodología

El desarrollo siguió spec-driven development con spec-kit: constitución (principios no negociables), especificación funcional con escenarios de aceptación, plan técnico, investigación de decisiones, modelo de datos, contratos y lista de tareas. Cada escenario de la especificación tiene una prueba automática con su código en el nombre (por ejemplo US2-03). El backend se construyó primero, sobre contratos probados, y el frontend después, cuando se cerró el diseño.

Capítulo 3

Especificación de los casos de uso principales

CU-01 · Buscar batería por autoComprador · Prioridad P1
PrecondiciónHay vehículos con medidas cargadas y productos activos.
Flujo principal1. El comprador elige la marca; el sistema lista solo marcas con datos.
2. Elige el modelo de esa marca.
3. Elige el año; si el modelo no distingue años, el paso se saltea.
4. El sistema resuelve las medidas de los vehículos que cubren ese año, más los que valen para todos los años.
5. Muestra los productos activos con stock de esas medidas, agrupados por gama, económicas primero.
6. Guarda el auto en el dispositivo para la próxima visita.
Alternativas4a. El auto no está cargado: "Todavía no tenemos cargado tu auto" y WhatsApp con marca, modelo y año.
5a. No hay stock de la medida: "Sin stock para tu auto" y WhatsApp.
EndpointsGET /vehiculos/marcas, /modelos, /anios, /compatibles
PruebasUS1-01 a US1-05, US1-10
CU-05 · Confirmar compraComprador · Prioridad P1
PrecondiciónCarrito con al menos un producto activo con stock.
Flujo principal1. El comprador completa nombre, DNI, teléfono y mail (cada campo explica para qué se usa).
2. Elige colocación (con zona y dirección) o retiro.
3. Elige el medio de pago; el sistema cotiza en el servidor (POST /checkout/cotizar) y muestra subtotal, descuento, costo de zona y total.
4. Confirma (POST /pedidos). En una transacción: descuenta stock con un UPDATE condicional, crea el pedido con número correlativo, guarda el comprador con el DNI cifrado, registra el evento y encola los mails.
5. Devuelve número, enlace de seguimiento e instrucciones de pago según el medio.
Alternativas1a. DNI con letras: "El DNI tiene solo números, sin puntos".
2a. Colocación sin dirección: "Falta la dirección para ir a colocarla".
3a. Con colocación, "Efectivo al retirar" no se ofrece.
4a. Otro comprador se llevó la última unidad: 409 "Se agotó mientras comprabas"; el stock nunca queda negativo.
4b. Precio alterado en el navegador: se ignora; vale el precio del servidor.
ReglasImportes en centavos enteros, siempre calculados en el servidor. Límite de pedidos sin pagar por comprador. Rate limit por IP.
PruebasUS2-01 a US2-06, US2-15
CU-06 / CU-27 · Pagar con Mercado Pago y notificaciónComprador y Mercado Pago
Flujo principal1. Al crear el pedido se genera una preferencia de Checkout Pro con external_reference = pedido.id, vencimiento de 30 min y solo medios instantáneos.
2. El comprador paga en Mercado Pago y vuelve a la tienda.
3. Mercado Pago llama al webhook. El sistema valida la firma x-signature (HMAC-SHA256) y consulta el pago a la API de Mercado Pago.
4. Si está aprobado y el monto coincide, registra el pago (único por medio, id_externo) y pasa el pedido a pagado con cambiarEstado.
Alternativas2a. Vuelve con "aprobado" en la URL pero sin aviso verificado: "Estamos confirmando tu pago".
3a. Firma inválida: se rechaza sin cambios.
3b. Aviso repetido: se procesa una sola vez y sale un solo mail.
4a. Monto distinto o pedido cancelado: no se marca pagado; se crea una alerta.
4b. Pago rechazado: el pedido sigue pendiente y se puede reintentar (CU-10).
PruebasUS2-07 a US2-12
CU-16 · Confirmar transferenciaAdministrador · Prioridad P2
PrecondiciónSesión válida en el panel; pedido por transferencia en "pendiente de pago".
Flujo principal1. Mateo ve la transferencia acreditada en su banco.
2. Abre el pedido y toca "Confirmar transferencia"; acepta la confirmación.
3. El sistema registra un pago manual con monto y usuario, pasa el pedido a pagado y encola el mail al comprador.
Alternativas3a. El pedido ya venció o cambió de estado: 409 y se informa; no hay reactivación automática.
PruebasUS3-03, US3-06, US3-07
CU-13 · Ingresar al panelAdministrador
Flujo principal1. Escribe su mail en /panel/ingresar.
2. El sistema responde siempre lo mismo (202) y, solo si el mail está autorizado, envía un enlace con un token aleatorio de 32 bytes; guarda su hash SHA-256 con vencimiento de 15 min.
3. Al abrir el enlace se marca como usado, se crea una sesión opaca en la base y una cookie httpOnly, Secure, SameSite=Lax de 30 días.
Alternativas2a. Mail no autorizado: no se envía nada, misma respuesta.
3a. Enlace vencido o usado: vuelve al ingreso con un mensaje claro.
Sin sesión, cualquier pantalla del panel redirige al ingreso.
PruebasUS3-01, US3-02
CU-23 · Importar planillasAdministrador · Prioridad P2
Flujo principal1. Sube un CSV de productos o de compatibilidades.
2. El sistema lo valida fila por fila con Zod.
3. Productos: upsert por SKU (los nuevos entran "a revisar"). Compatibilidades: upsert por marca, modelo, años y motor.
4. Devuelve un informe: filas totales, correctas, con error, creadas y actualizadas, y el motivo de cada error con su número de fila.
Alternativas2a. Medida inválida o campo faltante: la fila se informa y el resto se carga.
PruebasUS5-01, US5-02, US5-07

Capítulo 4

Arquitectura general

El sistema es una aplicación web con tres procesos propios (frontend, API y worker) y una base PostgreSQL, todos en contenedores Docker en un VPS Linux. Nginx termina HTTPS y enruta: /api va al backend y el resto al frontend. El navegador nunca habla con la base ni tiene claves: todo pasa por la API.

Patrones de diseño aplicados

Puertos y adaptadores

Mercado Pago, mails, fotos y revalidación detrás de interfaces chicas; reales en producción, falsos en pruebas.

Máquina de estados centralizada

Una tabla de transiciones pura y una única puerta, cambiarEstado, que bloquea la fila y aplica los efectos.

Unidad de trabajo

Crear un pedido, reservar stock, guardar el comprador y encolar mails ocurre en una sola transacción.

Value object Dinero

Importes en centavos enteros (bigint) con operaciones seguras; nunca números flotantes.

Strategy por medio de pago

Cada medio define si aplica descuento, si está disponible para la entrega y su vencimiento.

Outbox transaccional

Los mails se escriben en la misma transacción del cambio; el worker los envía con reintentos.

Idempotencia por restricciones

UNIQUE en pagos externos y en el outbox: un aviso repetido no cambia nada dos veces.

Capa anticorrupción

El scraper solo genera planillas; nunca escribe en la base. Si una fuente cambia, se arregla el scraper.

Ejemplo: la máquina de estados es código puro

const TRANSICIONES: Record<EstadoPedido, EstadoPedido[]> = {
  pendiente_pago: ['pagado', 'cancelado'],
  a_pagar_en_local: ['entregado', 'cancelado'],
  pagado: ['en_camino', 'listo_para_retirar', 'cancelado'],
  en_camino: ['entregado'],
  listo_para_retirar: ['entregado'],
  entregado: [],
  cancelado: [],
};

export function transicionesPermitidas(estado: EstadoPedido, entrega: Entrega) {
  return TRANSICIONES[estado].filter((a) => {
    if (a === 'en_camino') return entrega === 'colocacion';
    if (a === 'listo_para_retirar') return entrega === 'retiro';
    return true;
  });
}

Ejemplo: importes calculados en el servidor

export function calcularImportes({ lineas, descuentoPct, aplicaDescuento, costoZona }) {
  let subtotal = Dinero.cero();
  let descuento = Dinero.cero();
  for (const l of lineas) {
    subtotal = subtotal.sumar(l.precioUnitario.por(l.cantidad));
    if (aplicaDescuento)
      descuento = descuento.sumar(l.precioUnitario.porcentaje(descuentoPct).por(l.cantidad));
  }
  return { subtotal, descuento, costoZona, total: subtotal.restar(descuento).sumar(costoZona) };
}

El descuento se calcula por unidad, igual que el "precio por transferencia" de la ficha, para que lo que el comprador vio sea exactamente lo que paga.

La función cambiarEstado

  1. Abre una transacción y bloquea la fila del pedido (SELECT … FOR UPDATE).
  2. Valida la transición contra la tabla y la forma de entrega. Si no es válida, registra el intento con rechazado = true y responde 409.
  3. Aplica los efectos: devolver stock al cancelar, registrar el pago manual.
  4. Registra el evento (estado anterior, nuevo, actor y motivo).
  5. Encola los mails del comprador y del administrador según el mapa de eventos.
